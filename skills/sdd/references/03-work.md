# 工程: 実装・進捗・引き継ぎ

## 0. ゲート検証

medium / large は `approvals.plan`、small は `approvals.spec` に承認日があることを確認する。無ければ停止し、該当工程へ戻る。

## 1. 着手

- `_config.md` リリース運用の「ブランチ運用」に従い、作業ブランチを確認・作成する(規定の無いまま main 上で実装を始めない。項目が未記載なら references/01-intake.md §0 に従い補完する)。
- status を `doing` に変更し、`updated` を更新して backlog.py を実行する。同梱運用では main へ同期する(§5)。
- 記録先は log.md(small は票内の「作業ログ」節)。無い場合(旧運用で作成された票)は `references/templates/log.md` から作成する。

## 2. 作業中の記録

区切り(コミット・検証実施・問題発覚・セッション終了前)ごとに:

- 引き継ぎサマリ(現状 / 次の作業 / 未確定点)を最新状態へ**上書き**する。基準は「別セッションのエージェントがこの節だけで作業を再開できること」。
- 時系列ログへ日付付きで**追記**する(検証結果の詳細もここ。spec.md / plan.md には書かない)。
- plan.md の作業項目・検証チェックを消化状況に合わせて更新する。
- git が保持する情報の重複記録は避ける。参照が必要ならブランチ名・PR 番号を優先する(コミットハッシュは squash・rebase で無効になり得る)。

セッション再開時・コンテキスト圧縮後は、log.md の引き継ぎサマリと git log を読み直してから再開する。

## 3. 要件変更・昇格(降格なし)

### 昇格を伴わない要件変更

G1 承認後に確定要件・受入条件が変わる場合(規模判定は変わらない)、spec.md(小規模は票)の確定要件・受入条件を更新し、変更部分について G1 の再承認を得る。承認を得たら `approvals.spec` と `updated` を新しい承認日で更新し、backlog.py を実行する。変更の経緯は log.md の時系列ログに記録する。計画に影響する場合は plan.md も更新し、G2 の再承認を併せて得る。

### 昇格

作業中に新たな設計判断・未確定点が現れたら規模を一段上げる:

- **small → medium**: ディレクトリ `T-NNN_件名/` を作り票を spec.md へ転換(経過は log.md へ分離)し、規模判定の変更と要件の変更部分について G1 の再承認を得る。その後 plan.md を作成して G2 承認を得る。
- **medium → large**: 追加の設計判断・代替案を spec.md / plan.md へ反映し、変更部分について G1 / G2 の再承認を得る。

frontmatter の `scale` と `approvals.spec`(再承認日)を更新し、backlog.py を実行する。同梱運用では main へ同期する(§5)。

## 4. 停滞

外部要因(リリース待ち・ユーザー実施待ち等)で進められない場合は status を `blocked` にし、待ち内容と再開条件を引き継ぎサマリへ明記する。同梱運用では main へ同期する(§5)。

再開条件が満たされたら status を `doing` に戻し、`updated` を更新して backlog.py を実行する(同梱運用では main へ同期する)。完了処理へ直接進む場合は references/04-done.md に従う。

## 5. main への同期(同梱運用)

`_config.md` リリース運用が「実装ブランチに同梱」のプロジェクトでは、状態変化(G1/G2/G3 承認・status 変更)が作業ブランチ上で生じるたびに当該タスクの票を main へ同期する(粒度を変える場合は `_config.md` に記載)。main 側の票は同期時点のスナップショットであり、正は作業ブランチ側のまま(常時規則5)。同期を怠ると、main 起点で状況確認するセッションが古い status を報告し、誤報告・二重着手の原因になる。

手順(main へ直接コミットできる場合):

1. main 上で `git checkout <作業ブランチ> -- docs/tasks/<タスクディレクトリまたは票>` を実行する。
2. 昇格等で票のパスが変わった場合(例: `T-NNN_件名.md` → `T-NNN_件名/`)、main 側に残る旧パスを `git rm` する(checkout は削除・改名を伝播しない)。
3. backlog.py を実行して BACKLOG.md を再生成し、docs コミットする。

main が保護ブランチの場合は docs 用ブランチ上で同手順を行い PR を作成する。同期 PR は複数タスク・複数状態変化をまとめてよい。ただし G3 承認後の完了記録(アーカイブ移動・BACKLOG 再生成を含む)は本節ではなく `_config.md`「完了記録の載せ方」に従う(references/04-done.md §3)。

票はタスクごとに別ディレクトリのためブランチ間で編集は重ならない。唯一共有される BACKLOG.md は生成物であり、競合したら手で解消せず再生成する(常時規則4)。
