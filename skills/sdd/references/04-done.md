# 工程: 検証・完了判定(→ G3)

## 0. 前提確認

- 受入条件を満たし、検証チェックリストの「エージェント実施」分が全消化であること。
- 「実環境・ユーザー実施」分が残る場合は done にできない。status を `blocked` とし、残項目と実施依頼を報告して停止する。同梱運用では main へ同期する(references/03-work.md §5)。
- `_config.md` のリリース運用を確認する(項目が未記載なら references/01-intake.md §0 に従い補完する)。「G3 の時期」が「マージ・本番反映の確認後」の場合、反映確認が取れるまで G3 を求めない(リリース待ちは `blocked`、references/03-work.md §4)。

## 1. 仕様書反映の起案

spec.md(または票)の「仕様書反映」節を最終化し、恒久仕様書への反映内容を提示する。

- **delta 反映可**: 追加/変更/削除それぞれの対象節と反映後の文面。削除には理由を付す。
- **不定形**: 反映箇所と文面を自由記述で提示する。
- **スキップ設定**: 反映なしである旨を報告する。
- **実装 PR 同梱設定**: 反映は実装 PR で済んでいる。恒久仕様書の現状と spec.md の反映節が一致することを確認し、追認を求める(完了処理 §3.1 は不要)。

## 2. G3 承認

検証全消化の確認と仕様書反映内容をまとめて提示し、承認を求める。

## 3. 完了処理(承認後)

1. 恒久仕様書へ反映する(delta をマージ)。反映後はタスク文書側の記載は正ではなくなる(履歴扱い)。
2. frontmatter に `approvals.done: <日付>`・`status: done`・`updated` を記録する。
3. タスク(ディレクトリまたは票)を `docs/tasks/archive/` へ移動する(git 管理下なら git mv)。
4. backlog.py を実行し、BACKLOG.md の索引を更新する。
5. 完了報告(反映した仕様書の節・アーカイブ先)を行う。

main が保護ブランチで完了処理を直接コミットできない場合は、docs 用ブランチから PR を作成する(手順は references/03-work.md §5)。PR の粒度は `_config.md`「完了記録の載せ方」に従う。

## 廃番(完了せず破棄する場合)

- 破棄理由・関連ブランチや残存物の扱いを票に記録し、frontmatter に `status: dropped`・`updated` を記録したうえで archive/ へ移動する(アーカイブ索引で done と区別するため)。
- backlog.py を実行する(アーカイブ表に dropped として載る)。BACKLOG.md の「廃番」節(手書き)には追記しない。同節は票ファイルを持たない欠番 ID の記録に限る。ID は再利用しない。
