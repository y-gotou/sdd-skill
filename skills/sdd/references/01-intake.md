# 工程: 起票・要件定義(→ G1)

## 0. 前提確認(_config.md)

### _config.md が無い場合(初回セットアップ)

起票の前に以下を行う。

1. `references/templates/config.md` を複製し、ユーザーに確認しながら記入する:
   - 恒久仕様書のパスと形式(章立てあり=delta 反映可 / 不定形=自由記述で反映)。
   - 仕様書が無い場合は「最小限の As-Built 仕様書を新規作成する」か「反映工程をスキップする」かをユーザーが選択する。
   - 検証系統(このプロジェクトで利用できる検証手段の一覧)。
   - リリース運用(タスク文書の載せ方・ブランチ運用・main への同期・仕様書反映のタイミング・G3 の時期・完了記録の載せ方)。保護ブランチの有無を確認して選ぶ。
2. `docs/tasks/` と `docs/tasks/archive/` を作成し、backlog.py を実行して BACKLOG.md を初期生成する。

### _config.md が有る場合(必須項目の検証)

`references/templates/config.md` の項目(恒久仕様書・検証系統・リリース運用の各項目)が揃っているか確認する。適用条件付きの項目(「main への同期(同梱の場合)」「完了記録の載せ方(保護ブランチの場合)」)は条件に該当する場合のみ確認する。欠落があれば(テンプレート改訂前に作成された設定に生じ得る)、起票を進める前にユーザーに確認して補完する。

### 形式外ファイルの移行(backlog.py が警告した場合)

`docs/tasks/`(archive/ 含む)にスキル形式でないファイル(frontmatter の無い旧形式票・平置き資料等)があると、backlog.py が警告付きで索引から除外する。警告が出たら、初回セットアップに限らず、扱い(frontmatter を付与して票化 / archive/ へ移動 / `docs/tasks/` 外へ移す)をユーザーに確認して解消する。

## 1. ID 採番

`docs/tasks/`(archive/ 含む)の既存 ID と BACKLOG.md の「廃番」節を確認し、最大値+1 を採番する。ID は再利用しない。backlog.py が採番候補を表示する。

## 2. 規模判定(G1 の承認対象に含める)

**小規模** = 次の4条件をすべて満たす:

1. 受入条件を3項目以内で書き切れ、要件に未確定点(ユーザーに確認しないと決められない事項)がない
2. 設計判断が不要(既存パターンの踏襲のみ。新規のデータ構造・画面・外部インタフェース・設定項目を伴わない)
3. 検証が全てエージェント実施で完結する(実環境・ユーザー実施の項目がない)
4. 恒久仕様書への影響が既存記載の軽微な修正に留まる(新しい節・要件の追加がない)

**中規模** = 小規模の条件を満たさないが、要件が1回のヒアリングで確定できる見込み。
**大規模** = 複数の設計判断を伴う / 仕様書の複数章にまたがる / 段階リリースが必要。

境界で迷う場合は一段上とする。

## 3. 要件ヒアリング(規模で段階切替)

- **小**: 受入条件の合意のみ。
- **中**: 未確定点を質問で潰し、受入条件を確定する。
- **大**: 未確定点の質問に加え、代替案(2〜3案)とトレードオフを提示して方式をユーザーが選択してから受入条件を確定する。

依頼が要件整理のみ(文書作成・実装を含まない)の場合、ヒアリングと要件案の合意は会話上で行ってよい。合意した要件案は G1 候補として保持し、文書生成(§4)と G1 承認日の記録(§5)はユーザーが作業開始を明示してから行う。

## 4. 文書生成

- **起票先ブランチ**: `_config.md` リリース運用の「ブランチ運用」に従い、票を作成するブランチ(main / 作業ブランチ)を確認する。作業ブランチ上で起票する設定なら、命名規則に従いブランチを作成してから票を作る。
- **件名**: 日本語または英数スラッグ(例: `T-002_login-fix`)。シェル操作・git 表示の都合で英数を選んでよい。
- **小**: `references/templates/single.md` から `docs/tasks/T-NNN_件名.md` を作成(scale: small)。検証方法も本票に記載し、G1 で併せて承認する(小規模に G2 は無い)。
- **中・大**: `references/templates/spec.md` から `docs/tasks/T-NNN_件名/spec.md` を、`references/templates/log.md` から log.md を同時に作成する。G1 前の代替案検討・G2 の経緯も log.md の時系列ログに記録する。
- **仕様書反映節**: `_config.md` が delta 反映可なら「追加/変更/削除」の差分形式で、不定形なら自由記述で反映方針を書く。反映スキップのプロジェクトでは「なし(設定によりスキップ)」と記す。

## 5. G1 承認

- 承認対象(規模判定・確定要件・対象外・受入条件。小規模は検証方法も)を一覧で提示し、承認を求める。最終ヒアリングの確認と G1 承認の提示は分けず、最後の質問への回答確認と併せて一括で承認を求めてよい。
- 承認を得たら frontmatter に `approvals.spec: <日付>` と `updated` を記録し、backlog.py を実行する。作業ブランチ上での承認なら main へ同期する(references/03-work.md §5)。
- **G1 承認前に plan.md の作成や実装へ進まない。**
